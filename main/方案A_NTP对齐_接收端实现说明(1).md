## 1. 背景与总体架构

**要解决的问题**: N 台音箱各播各的, 起播时刻由"包到达+水位"决定, 台间偏差
不可控(几十~几百 ms)。目标: 任意两台播同一音频帧的时刻差 < **5ms**
(人耳对音箱间相位差的感知门限约 5~10ms)。

**手段**: 发送端把 RTP `ts` 字段定义为 **绝对墙钟**(对齐后 = 世界时间),
所有音箱也持有同一墙钟(NTP 对齐发端)。播放不再看"包何时到", 而看
"这个 ts 约定在哪个墙钟时刻播" —— 到达抖动只影响缓冲水位, 不影响播放时刻。

```
                     ┌──────────────── 发端 ESP32-S31 ────────────────┐
 外网 pool.ntp.org ──▶ SNTP客户端(自我校准, smooth)                    │
 (有WAN时)           │                                                │
                     │ ntpd 应答服务 UDP:123  ──内网───────────┐       │
                     │ RTP 发送 :5004 (ts=墙钟×48k, 1ms/包)    │       │
                     └────────────────────────────────────────┼───────┘
                                                            ▼
      ┌── 音箱1: SNTP客户端──▶发端:123   收 RTP :5004 ──▶ 按due时刻播放
      ├── 音箱2: SNTP客户端──▶发端:123   收 RTP :5004 ──▶ 按due时刻播放   台间差
      └── 音箱N: ...                                                ≈1~3ms
```

**对时精度预期**(内网 WiFi, NTP 往返补偿后): 音箱 vs 发端 **±1~3ms**。
对比: 各自对外网 pool.ntp.org 对时, 台间相对误差 10~30ms 且依赖路由器 WAN。
精度若未来要 <0.1ms, 备选演进见附录 D(RBS), 当前不做。

## 2. RTP ts 语义(发送端已定, 勿改)

发送端代码事实(`main/rtp_send.c`), 接收端按此解析:

- **锚定**: 发送起流(从无订阅到有)时取绝对墙钟:
  `ts0 = tv_sec × 48000 + tv_usec × 48 / 1000`  (即 unix 秒换算成 48kHz tick,
  µs 精度)
- **推进**: **每个 1ms 节拍 `ts += 48`(无论该拍是否取到音频块, 2026-11-13 修)**。
  修前只在取到块时推进 → 每次节拍跳过 ts 永久落后墙钟 1ms(rxplay NTP-e2e 实测
  67min 累计 64ms 线性增长), due 调度下会吃掉 PLAY_DELAY; 修后跳拍只留音频洞
  (垫片/FEC 兜住), 时间轴忠实墙钟(±晶振 ppm 级漂移, 会话内可忽略)
- **取值域**: 32bit, 回绕周期 **2^32/48000 ≈ 24.86 小时**(回绕处理见 §5.2)
- **节拍**: esp_timer 1ms/包(实测 avg=1000µs, 99.9% 在 ±0.3ms 内) ——
  **ts 时刻 ≈ 包的实际发送墙钟时刻**, 偏差 < 1ms
- FEC 包(pt=97)的 seq = 所覆盖组组首 seq − 1; **FEC 恢复以 seq 对齐为准,
  不使用其 ts 字段**
- 数据/发现/控制口完全不变:
  `:5004 数据(pt=96 媒体 / pt=97 FEC)`, `:6000 发现(pt=98)`, `:6010 控制`,
  `SSRC=0x7C41`, 载荷格式 v1.2 逐字节不变(事实源: `main/ar_proto.h`)

## 3. 接收端功能清单

### F1. SNTP 对时(必做, 可照做)

**核心原则: 时基跟着流走 —— NTP 服务器 = 首个 RTP 包的源 IP。**

不要写死服务器 IP, 也不要在上电时就启动。必须等第一个 RTP 包到达, 用
`recvfrom` 的 `from.sin_addr` 作为 SNTP 服务器。原因: 发端 IP 会变
(DHCP/换网段), 写死就会像 2026-11-13 现场那样 —— 8 台音箱收流完全正常、
发端统计速率也对, 但**没有一台来对时**, 结果全部静音。

**严格按这个顺序实现**:

```c
/* ① 收流线程: 首个 RTP 包到达时, 把发端地址当 NTP 服务器启动 */
if (!s_ntp_started) {
    s_ntp_started = true;
    sntp_start(from.sin_addr.s_addr);      /* 发端 = 流源, 零配置 */
}
```

```c
/* ② 启动 SNTP: 用 esp_netif_sntp, 不要手写 NTP 协议栈
 *    (库已处理 32 位秒回绕/KoD/闰秒; 且会 settimeofday, 之后
 *     gettimeofday 拿到的就是对时后的钟, ts 直接可比) */
static void sntp_start(uint32_t srv_ip)      /* srv_ip = 网络序 */
{
    esp_ip4_addr_t a = { .addr = srv_ip };
    char ip[16];
    snprintf(ip, sizeof(ip), IPSTR, IP2STR(&a));

    if (s_ntp_inited) esp_netif_sntp_deinit();   /* 换发端时先停旧的 */
    esp_sntp_config_t cfg = ESP_NETIF_SNTP_DEFAULT_CONFIG(ip);
    cfg.smooth_sync = false;   /* !! 必须 false(见下表坑 2) */
    cfg.start = true;
    esp_netif_sntp_init(&cfg);
    s_ntp_inited = true;
}
```

```c
/* ③ 播放门控: 同步完成前不开播(避免用错时基各台错位) */
bool ntp_ready(void) { return s_ntp_synced; }   /* 由事件回调置位 */
/* 事件: ESP_NETIF_SNTP_TIME_SYNCED -> s_ntp_synced = true */
```

**三个必须注意的坑**

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | 写死/猜 NTP 服务器 IP | 发端串口一直打 `授时请求: 无`, 全箱静音 | 用首个 RTP 包的源 IP |
| 2 | `smooth_sync` 保持默认 true | 开机钟(1970 起点)只被 µs 级缓调, 永远追不上, `synced` 恒 false | **`smooth_sync = false`**(跳步一次, 在起流前完成无碍) |
| 3 | 只启动不等待就开播 | 起播前几秒各台错位 | 播放线程先查 `ntp_ready()` |

**超时兜底**: SNTP 启动后 10s 仍未同步 → 打一条 WARN, 并进入 §5 的降级行为
(按 seq 顺序播放), **不要无限等待**。

**状态可见(联调必需)**: 把 `synced(0/1)` 与对时 offset 估计值打进 5s 统计行
(见 §F3)。发端侧另有独立观测, 见 §9 —— 排查时先看发端, 不依赖音箱串口。

### F2. 按 ts 约定时刻播放(核心, 现有播放循环改造)

1. **环形缓冲改存包内 RTP ts**(当前若存"到达时刻"需换, 到达时刻另存供统计)。
2. **due 计算**: 包播放时刻 = 墙钟换算
   `due_us = (uint64_t)(扩展后的 ts) / 48000 × 1e6 + PLAY_DELAY_US`
   (`PLAY_DELAY_US` 建议 80ms 起评, 见 §6; 换算用对时后的 gettimeofday)。
3. **调度规则**(替换现"攒水位即播"):
   - 头包 `due` 未到: 等待(短睡/自旋预算 ≤1ms), 不提前播;
   - 到点: 出队写入 I2S;
   - 迟到(现已过 due + 容忍窗, 如 20ms): 整包丢弃快进, 保证延迟不爬升
     —— 天然取代现有 late_drop 启发式;
   - 网络洞: 沿用 hold&decay 垫片(已合入), 与 due 调度正交。
4. **起播门控**: 未对时(`!time_synced`)不出声、按到达模式不降级播放
   (避免错误时基造成各台错位); 对时完成后自动起播。
5. **ts 回绕**: 收包侧做 32→64 高位扩展(缓存高 32bit, 差值跳变 >2^31 时进位/
   借位), due 计算全用 64bit。
6. **发端重启/重锚检测**: 新包 ts 与本地推算偏离 >1s ⇒ 视为新会话, 重置
   due 基准(丢弃旧缓冲重新缓存 PLAY_DELAY)。

### F3. 诊断(联调必需)

5s 统计行增加: `synced(0/1) ntp_off_ms | due_late(丢包数) wait_avg_ms
wm_ms(水位)`。没有这些, 现场无法分辨"对时误差"还是"调度偏差"。

## 4. 通信协议接口

### 4.1 NTP(新增, 唯一新协议)

| 项 | 值 |
|---|---|
| 传输 | UDP, 服务器端口 **123**, 客户端任意端口 |
| 报文 | 标准 NTP 48 字节(请求只需 LI_VN_Mode=0x1B, 其余 0) |
| 发端应答 | LI=0(正常) / VN=回显 / **Mode=4** / **Stratum=1** / RefID=`ARNT` / Ref/Recv/Xmit 时间戳=发端本地钟 / Originate=回显客户端 Xmit |
| 客户端库 | `esp_netif_sntp`(两端同款), offset=½[(t1−t0)+(t2−t3)] |
| 查询节奏 | 同步期库默认(指数退避数秒一次); 稳态 1 次/小时足够 |
| kiss-of-death | 发端不发, 无需处理 |
| 失效行为 | 发端离线 ⇒ SNTP 超时, 音箱保持旧钟(µs 级晶振, 小时漂移 <50ms), 播放不受影响 |

### 4.2 RTP/发现/控制(全部不变)

音箱现有解析逻辑零改动; 唯一新增 = 使用 ts 字段的绝对语义(§2)。
音箱**不需要**改动 :6000 发现包内容与 :6010 行为。

### 4.3 配网/配置新增字段(可选但建议)

`ntp_server` (string, 默认空=自动跟随 RTP 源 IP)。
BLE/Web 配网表单各加一项即可, 无协议格式变化。

## 5. 边界与异常行为(两端约定)

| 场景 | 音箱行为 |
|---|---|
| 未对时收到流 | 静默缓存(≤PLAY_DELAY), `time_synced` 后起播; **若 10s 仍未同步则降级为按 seq 顺序播放**(能出声但台间不同步, stat 行标 `synced=0`, 便于现场区分"没声"与"不同步") |
| 对时中(SNTP 进行时) | 同上 |
| NTP 服务器不可达 | 用上次钟继续, stat 行标 `synced=0`; 播放不中断 |
| ts 回绕(24.86h) | §F2-5 高位扩展, 无感 |
| 发端重启(ts 重锚) | §F2-6, >1s 跳变判新会话重缓存 |
| 发端暂停发送(tx_enable=0) | seq/ts 冻结, 音箱缓冲耗尽后静音(hold&decay), 恢复后 ts 续 —— 无需特殊处理 |
| 迟到包洪泛(网络劣化) | due-late 丢弃计数上报; 水位上限 = PLAY_DELAY, 防延迟爬升 |

## 6. 延迟预算(PLAY_DELAY 取值依据)

```
采集对齐(bus池)  节拍  网络转发   WiFi到达抖动   播放延迟
 ~16ms  +        1ms  + ~1ms  +   p99≈7ms      + PLAY_DELAY
```

- 起评 **PLAY_DELAY = 80ms**: 覆盖上述全部 + 余量, 端到端 ≈ 100ms;
- 联调后按实测 due_late/wait 分布逐步下调(目标可到 30~40ms);
- 发端节拍已实测均匀(±0.3ms), 不构成预算主体, 主体是 WiFi 到达长尾。

## 7. 验收标准

**Phase 1(F1 对时)**:
- [ ] 音箱 `time_synced` 后, offset |Δ| < ±5ms(与发端 /stat 的墙钟比对);
- [ ] PC 侧 `w32tm /stripchart /computer:<发端IP> /samples:5` 显示发端
      NTP 应答正常(联调用)。

**Phase 2(F2 同步播放)**:
- [ ] 两台音箱同播 1kHz 正弦, 手机单点录音做互相关, 相位差 < 5ms;
- [ ] 端到端延迟(发端播放源 vs 音箱出声) ≤ 100ms;
- [ ] 24h 连续运行: 无因 ts 回绕/对时刷新导致的卡顿或错位。

## 9. 发端侧授时观测(排查第一站, 不需要音箱串口)

发端 ntpd 每 5s 打一行观测(2026-11-13 新增), 串口 921600 直接看:

```
I (11501) ar.ntpd: 授时请求: 无(音箱 SNTP 未指向本机 IP :123)
I (45649) ar.ntpd: 首次授时请求 192.168.3.25, 钟差 -828ms
I (47889) ar.ntpd: 授时请求(累计): 192.168.3.25 n=3 2s前 -828ms
```

| 字段 | 含义 | 判读 |
|---|---|---|
| `无` | 5s 内没有任何设备请求 | **收端 SNTP 未启动或指向错** —— 最常见, 见 §10 第 1 行 |
| `首次授时请求 <IP>` | 某设备第一次来 | 说明收端接通了, 链路 OK |
| `n=` | 该 IP 累计请求次数 | 应缓慢增长(同步期数秒一次, 稳态 30s~1h 一次) |
| `Xs前` | 距上次请求的秒数 | >3600 说明周期过长, 晶振漂移会累积 |
| `±Xms` | 该客户端钟差(客户端 − 发端) | 正常 ±5ms 内; 几百 ms 以上说明未收敛或链路异常 |

> 注: `钟差` 是把请求包里的 transmit 字段与发端收到时刻相减, 含单程链路
> 延迟(内网 1~3ms)。若用手工工具发未填 transmit 的裸包(如 rxplay 的
> `0x1B`+47×0), 这个值无意义 —— 只看 `n=` 与 `Xs前`。

### 实测基线(8 箱环境, 供对照)

| 指标 | 实测值 | 说明 |
|---|---|---|
| 发端钟 vs PC 精确 offset | **-828ms**, 10 次极差 9ms | 发端无外网, 钟比 PC 慢约 0.8s; 对"台间同步"无影响(都对发端) |
| 发端应答 RTT(PC 侧) | 中位 4.9ms, max 10ms | ntpd 优先级已由 2 提升到 3, 不再出现负 RTT |
| 发端 ts 推进 | 4ms 包间隔 192 tick, ≈1.004× 实时 | 正常(每拍推进, 跳拍也推进) |

## 10. 故障对照表(现场按顺序查)

| 现象 | 发端 `授时请求` 行 | 结论 / 动作 |
|---|---|---|
| 全部静音, 但发端 `spk=` 速率正常 | `无` | **收端 SNTP 没启动或 IP 指错**(2026-11-13 事故)。按 §F1 改成跟随流源 IP |
| 全部静音 | 有请求, 钟差几百 ms 以上 | 时钟未收敛: 检查 `smooth_sync=false` 是否生效 |
| 部分箱静音 | 有请求, 但这些箱不出现 | 该箱固件版本旧 / 配网异常 |
| 有声但台间不同步 | 各箱都有请求且钟差正常 | 不是授时问题, 查 §F2 的 due 调度与 PLAY_DELAY |
| 有声但某些声道没声 | 无关 | 查声源本身: 实测 L/SL/SBL 三路源信号就是数字静音(-50dBFS), 不是链路问题 |
| 发端重启后短暂静音 | 钟差突变 | 正常: 发端 ts 重锚, 收端按 §F2-6 判新会话重缓存, 1~2s 恢复 |

## 附录 B. 为什么不继续用外网 SNTP 对齐

家宽上下行不对称(如 40/8ms)使 SNTP 单次对时偏差 ±10~20ms; 各音箱独立对
公网, 台间相对误差 10~30ms, 超听感门限; 且依赖路由器 WAN。方案 A 对齐
ts 的产生者(发端), 同构路径误差相消。

## 附录 C. 术语

- due: 某包约定播放的墙钟时刻 = ts 换算 + PLAY_DELAY
- 水位(wm): 环形缓冲内可播毫秒数; 本方案中上限被 PLAY_DELAY 约束
- hold&decay: 丢包垫片策略(保持上一样本指数衰减), 已在音箱端合入

## 附录 D. 演进路线:<0.5ms 级同步的设计(记录, 触发后实施)

> 触发条件: 出现"同一房间多箱声像定位 / 多房间 <0.5ms"真实需求。
> 参考: <https://github.com/dfki-in-icc/OpenWiFiSync>(RBS, ESP32+商用 AP
> 实测 ±30µs, GPLv3 —— **思想可鉴, 代码不可抄**; 算法自实现无传染)。

**D.1 原理**: 参考事件必须是"发端与所有音箱都能观测的同一物理事件"。
本系统天然存在 —— **AP 信标**(发端 STA 与全部音箱 STA 同信道接收)。
发端自身的广播不可用作参考(发端听不到自己; 单向时间戳含 CSMA/驱动
不确定度 ~1ms, 无收益)。两条路线按成本排序, 先探针后实施。

**D.2 路线 1: TSF 硬件公共时基(首选, ~50 行/端)**

STA 的 TSF 定时器由硬件在每个信标到达时自动对齐 AP 时钟, 所有 STA 的
TSF 读数天然共享同一时基(µs 级) —— "同一物理事件"的硬件实现, 无需
软件打时间戳。

- 发端: 1Hz 广播锚点帧(建议 UDP :6001), 载荷 `[rtp_ts_低32, 本机TSF读数]`;
- 音箱: 回归维护 TSF↔本地 esp_timer 映射( offset+频差, 抗单点抖动),
  播放调度 `due_tsf = 锚TSF + (目标ts − 锚ts)/48 × 1000 + PLAY_DELAY×1000`,
  循环读 `esp_wifi_sta_get_tsf()` 判到期;
- NTP 方案保留为回退路径(TSF 异常自动降级);
- 前置探针(半天): 两块板同一 GPIO 脉冲沿对比 TSF 读数差, 验证 S31
  pre-release 的 TSF API 可用性与稳定度 —— 不过关再走路线 2。

**D.3 路线 2: 软件 RBS(OpenWiFiSync 思想自研, 对标 ±30µs)**

- 各设备开 promiscuous 收信标, `esp_timer` 打到达时间戳(软件戳抖动
  10~50µs, 靠统计滤波压下去);
- 发端 10Hz 广播自己的信标时间戳表; 每音箱计算
  `Δ = 本机信标戳 − 发端信标戳`, 凸包/线性回归得 钟差+频差;
- 风险: S31 监听模式成熟度未知 —— 这也是路线 1 优先的原因。

**D.4 共同约束**: 音箱 modem-sleep 必须关闭(音频场景已关); 精度到位后
PLAY_DELAY 可由 80ms 压至 ~30ms(端到端 ≈50ms)。
